# 后端需求分析

## 1. 项目概述

工业管理 APP 后端服务，为 HarmonyOS 移动端提供 REST API 与 WebSocket 实时推送能力。采用 Spring Boot 技术栈，面向柔性组装产线的 MES（制造执行系统）教学/仿真场景。

**目标读者**：Java 后端开发者
**关联文档**：[前端需求分析](前端需求分析.md)、[后端SpringBoot设计书](../设计书/后端SpringBoot设计书.md)、[后端接口设计](../接口设计/后端接口设计.md)、[后端MySQL设计书](../数据库设计/后端MySQL设计书.md)

## 2. 核心需求

### 2.1 鉴权与权限（RBAC）
- 基于角色的权限控制（Role Based Access Control）
- 四个角色：admin、leader、operator、inspector
- JWT Token 认证
- 每个 API 方法挂权限码注解（如 @RequiresPermission("workorder.dispatch")）
- 登录后根据角色加载权限码集合

### 2.2 基础数据管理
- 车间（Workshop）管理：机加工车间、柔性车间、智能组装车间、SMT 车间
- 产线（Production Line）管理：名称、所属车间、当前工艺、当前工单、状态、支持工艺
- 工作站（Workstation）管理：编码、名称、所属产线、设备状态、工作状态、传送带状态、计数器
- 工艺（Process）管理：编码、名称、适用产品
- 工序（Process Step）管理：顺序号、OP 编码、名称、默认工作站
- 产品（Product）管理：编码、名称、默认工艺

### 2.3 人员管理（管理员）
- 增删改查人员信息
- 字段：姓名、工号、登录账号、初始密码、角色、所属车间/班组、状态、头像
- 按角色 Tab 切换列表
- 搜索（姓名或工号）

### 2.4 工单状态机（核心）
工单是系统的灵魂，状态机驱动所有页面变体：

```
                              ┌──── 报废 (终态) ────┐
                              │                      │
[待派工] ─派工→ [已派工] ─操作员开工→ [生产中] ─整线完成→ [生产完成（待报工）]
   │                                  │                       │
   │                            异常上报↓             操作员报工↓
   │                              [暂停中] ─恢复→[生产中]   [已报工]
   │                                                              │ 质检抽检
   │  仅在 "待派工" 状态可修改                                    ↓
   │                                                        班组长确认工时
   │                                                              ↓
   └─                                                          [完工] (终态)
```

**状态转换接口**：
- 创建 → 待派工
- 派工 → 已派工
- 开始生产 → 生产中
- 暂停（异常）→ 暂停中
- 恢复 → 生产中
- 报工 → 已报工
- 确认完工 → 完工
- 报废 → 报废

**业务校验规则**：
- 修改工单：只允许在 "待派工" 状态
- 派工：只允许在 "待派工"；同一操作员同一时间只能持有一个 "已派工/生产中/暂停中" 工单
- 开工：只有被指定的 operator 才能调 start；产线必须空闲
- 报工：只有 "生产完成" 才能报工；good + ng ≤ plan_qty
- 确认工时：建议要求至少一条 inspection_record
- 报废：从 "暂停中" 或 "已报工" 都可报废；终态后不可再改

### 2.5 产线仿真（核心难点）

**柔性组装线 7 个工作站固定顺序**：
OP10 上料 → OP20 主板组装 → OP30 后盖组装 → OP40 螺丝锁付 → OP50 激光打标 → OP60 成品检测 → OP70 下料

**仿真器设计**：
- 每条 "生产中" 的产线由一个独立 Scheduler 任务驱动
- Tick 周期建议 1 秒
- 每个工作站按工艺设定的节拍递增 raw / good / ng / processed_count
- 每次 tick 产生的变化写入 production_log 表
- 通过 WebSocket 推送给所有订阅 /topic/lines/{id} 的客户端
- 整线启动时初始化 Scheduler；停止/复位时取消任务；异常时挂起任务并广播异常事件
- 防止重复启动（同一产线 ID 只能挂一个任务），可用 Redis SETNX 或 ConcurrentHashMap 做幂等

### 2.6 异常管理
- 异常上报：弹窗输入 "异常描述" → 整线置为 "故障停机"，班组长收到待办
- 异常处理：班组长选 "复位"（清异常→继续生产）或 "停止+工单报废"
- 异常记录：关联工单、产线、工作站、上报人、处理人、处理动作

### 2.7 质检管理
- 对已报工工单做抽检
- 抽检数量建议为批量的 5% ~ 10%
- 录入：抽检数量、抽检良品、抽检 NG、不良原因描述、常见不良类型多选
- 提交完成后向班组长推送 "可确认工时" 待办

### 2.8 质检看板（Dashboard）
- 今日计划达成率 = Σ完工数 / Σ计划数（当天工单）
- 累计投入 = Σ raw
- 累计产出 = Σ finished
- 累计废品 = Σ ng
- 产品完工占比 = 完工数 / 计划数
- 工序完工占比 = 工序产出 / 工序计划
- 本月计划达成率 = 每日达成率序列（1~30 日柱状趋势）

### 2.9 实时状态同步（WebSocket）

**必须实时同步的协作场景**：
| 触发者 | 触发动作 | 同步对象 |
|--------|---------|---------|
| 操作员 | 启动/停止/复位整线 | 班组长（产线详情）、管理员（大屏）、质检员（待办） |
| 操作员/设备 | 异常上报 | 班组长 "异常待处理" 红色待办 |
| 工作站（仿真定时推进） | 状态变化 | 任何打开产线详情的人 |
| 班组长 | 派工 | 被指派操作员的 "我的工单" 列表 |
| 操作员 | 提交报工 | 质检员 "待抽检" 列表 |
| 质检员 | 提交抽检 | 班组长 "已报工" 详情的 "质检状态" |
| 班组长 | 确认完工/报废 | 工单列表、看板、操作员 "我的工单" |
| 管理员 | 修改人员/产线/工艺 | 各角色基础数据刷新 |

**推送通道选型**：
- WebSocket（首选）：双向、低延迟、产线 1Hz 刷新
- MQTT：工厂级 IoT 设备直连（未来扩展）
- HTTP 轮询：WS 断线兜底降级

**推荐架构**：
```
PLC/工作站设备 ─MQTT─> 后端(Spring Boot + EMQX/Mosquitto)
                              │
                              ├─ MySQL/PostgreSQL（落盘）
                              ├─ Redis（实时状态缓存 + Pub/Sub）
                              └─ WebSocket(STOMP) ─> 鸿蒙 APP/Web 端
```
教学/仿真版可省略 PLC 链路，用后端 Scheduler 模拟设备状态推进。

**WebSocket Topic 设计**：
- /topic/lines/{lineId} — 产线整体状态
- /topic/lines/{lineId}/stations — 该产线所有工作站状态（高频，1~2Hz）
- /topic/workorders/{workOrderId} — 单工单状态机变更
- /topic/exceptions — 全局异常事件
- /user/queue/todos — 按用户推送的 "我的待办"
- /user/queue/notifications — 按用户推送的系统通知

**消息体设计原则**：
- 推完整快照，不推增量
- 带版本号/时间戳
- 带幂等 ID

### 2.10 数据模型（14 张核心表）
1. user — 人员
2. workshop — 车间
3. production_line — 产线/资源
4. process — 工艺
5. process_step — 工序/工艺步骤
6. workstation — 工作站
7. product — 产品
8. work_order — 工单（核心）
9. work_order_route_step — 工单工艺路线快照
10. production_exception — 生产异常
11. inspection_record — 抽检记录
12. production_log — 产线运行日志（实时同步关键）
13. role_permission — 角色权限
14. line_process_support — 产线支持工艺关联

所有表带公共列：id、created_at、updated_at、version（乐观锁）、is_deleted（软删除）。

## 3. 接口需求

约 35 个最小可用接口，覆盖：
- 鉴权（3 个）
- 基础数据（7 个）
- 人员（4 个）
- 工单（10 个）
- 产线/工作站操作（6 个）
- 异常（3 个）
- 质检（3 个）
- 看板/待办（2 个）
- WebSocket 实时通道（6 个 Topic）

详见 [后端接口设计](../接口设计/后端接口设计.md)。

## 4. 非功能性需求

### 4.1 性能
- API 响应时间 < 200ms（P95）
- WebSocket 推送延迟 < 2 秒
- 产线仿真 Tick 1 秒周期稳定
- 支持多产线并行仿真

### 4.2 可靠性
- 状态变更接口加乐观锁，防止并发冲突
- WebSocket 断线后客户端可拉全量恢复
- 数据软删除，支持审计追溯

### 4.3 安全
- JWT 鉴权，Token 有过期时间
- 密码哈希存储
- SQL 注入防护（MyBatis-Plus）
- XSS 防护

### 4.4 可扩展性
- 保留 MQTT 接入点，未来接真实 PLC 设备只需改适配器
- Redis Pub/Sub 支持多实例后端横向扩展
- 数据模型预留 BOM、SOP、OEE 字段

## 5. 约束与假设

- 一个工单绑定一条产线，暂不支持跨线生产
- 一个操作员同一时间只能持有一个 "激活" 工单
- 确认工时建议强校验存在 inspection_record（业务校验，不做数据库强约束）
- 报工时录入的工时是 "申报工时"，可与系统计算的 "产线运行时长" 不一致
- 返工工单独立于原工单单独计件，但 source_workorder_id 关联原工单
- 异常上报会把工单切到 "暂停中"，恢复后回到 "生产中"，报废则进终态
